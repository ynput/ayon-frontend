# Addon frontends (module federation)

Addons ship frontend modules that the host loads at runtime with module federation. `RemoteModulesProvider` (`shared/src/context/remote-modules`) registers every addon's `remoteEntry.js` from `/api/frontendModules`. `useLoadModule` / `useLoadRemotePages` then load the modules where they render.

## One store, api and set of contexts

Addons import `@ynput/ayon-frontend-shared` from npm. The host itself uses the same code from source (`@shared`). Without sharing, each addon would get its own copy of everything in that package: its own RTK Query `api` with its own cache, and its own React contexts. It would then need its own store and providers, and nothing would reach the host's cache.

The host shares these as singletons, so an addon that declares the same shares uses the host's instances:

| Package | How the host provides it |
| --- | --- |
| `react`, `react-dom`, `@ynput/ayon-react-components` | `shared` in the federation plugin (`vite.config.ts`) |
| `@reduxjs/toolkit`, `react-redux`, `react-router`, `react-router-dom`, `react-toastify`, `primereact/confirmdialog`, `@ynput/ayon-frontend-shared` and every subpath (`/api`, `/context`, `/Slicer`, ...) | `registerShared` at startup, with the host's own modules (`hostSharedModules.ts`, called from `src/index.tsx`) |

What an addon gets from that:
- RTK Query hooks from `/api` read and write the host's cache. A tag the host invalidates refetches addon queries and the other way round. A query the host already ran isn't requested again.
- Endpoints the addon injects (`api.injectEndpoints`, `enhanceEndpoints({ addTagTypes })`) go into the host's api.
- Slices go into the host store: `slice.injectInto(rootReducer)`, or `rootReducer.inject(...)`. Middleware goes in with `addMiddleware`. All of these come from `/api` (`shared/src/api/base/store.ts`).
- Shared contexts such as `GlobalContext`, `PowerpackContext`, `ProjectContext`, `ProjectFoldersContext`, `SlicerContext` and `ViewsContext` are the host's. An addon module only needs a provider the host doesn't already render above it.
- `useNavigate`, `useParams`, `useLocation` and `useSearchParams` work in addon modules, because they read the host's router. Without the share an addon's own copy of react-router has no router above it and these hooks throw. The `router` prop the host still passes to pages is only for addons that don't share react-router.
- `toast()` shows in the host's toast container. An addon's own copy of react-toastify has no container on the page, so its toasts never show. The `toast` prop is kept for the same reason as `router`.
- `confirmDialog()` (and `confirmDelete` from `/util`) opens the host's app-level `ConfirmDialog`. primereact opens every mounted `ConfirmDialog` from the copy that `confirmDialog` came from, so an addon that shares `primereact/confirmdialog` must not mount its own: the dialog would open twice. An addon that doesn't share it keeps needing its own `ConfirmDialog` for its own `confirmDialog` calls. Only this subpath is shared; other primereact components stay per copy.
- Every module renders under the Redux `Provider`, `GlobalProvider` and `PowerpackProvider` (`app.tsx`). Project page modules are also under the project providers (`ProjectPage.tsx`).

`ayon-addon-full-template` shows the addon side: its federation config, a slice and endpoints.

## Slots and manifests (`@ynput/ayon-addon`)

The addon API lives in `addon/` (`@ynput/ayon-addon`, not published yet). The host builds it from source (alias in `vite.config.ts`, paths in both tsconfigs) and registers it in `hostSharedModules.ts`. Addons list it in their federation `shared` with `import: false`, so they never bundle a copy: everything they import from it is the host's.

- **Manifest.** An addon that lists `manifest` in `frontend_modules` and exposes `./manifest` declares its contributions there (`defineAddon({ contributes: [...] })`). The manifest imports from `@ynput/ayon-addon/manifest`, which the addon bundles (plain functions): the main entry is the host's copy, and a helper an older AYON doesn't have yet would be `undefined` and stop the whole manifest from loading. `RemoteModulesProvider` loads every manifest right after registering the remotes and calls `registerManifest`; then `setManifestsLoading(false)`. Addons without a manifest keep keyword matching (`App`, `Project`, `Studio`, `Route`) unchanged.
- **Registry.** A module-level store in `addon/src/registry.ts`, read with `useContributions(slot)`. Contributions are keyed `<addon>.<id>`. An unknown slot, an invalid id, a missing description field or piece, and duplicates are skipped with a console warning naming them (`addon/src/validate.ts`, also what `ayon-addon check` runs).
- **Slots.** `SlotMap` (`addon/src/slots.ts`) is the source of truth for each slot's description, context and pieces; `SLOTS` is what the host checks at run time. Adding a slot: one `SlotMap` entry, one `SLOTS` entry, a helper in `addon/src/slotHelpers.ts`, and the placement in the host. Discovery and loading don't change.
- **Page contexts.** `project.page` and `studio.page` contexts are built from the host's providers around the page (slicer, `ProjectFoldersContextProvider`, `WithViews`) in `shared/src/components/AddonLayout/pageSlotContext.ts`, used by `AddonPages.tsx` and the dev shell's stages: a new field goes there once. A page's `viewType` (validated against the server's `NAME_REGEX`) sets the `WithViews` view type, so the host shows the views menu and the page gets `views`. Views are stored per view type for the whole app, so `useAddonPages` hides a page whose view type AYON (`BUILT_IN_VIEW_TYPES` in `AddonPagesHelpers.ts`, keep it in step with new built-in view types), a legacy page or an earlier addon page uses.
- **Menu items.** Every menu-item slot has `position` (`top`: first; `bottom`, the default: after the menu's own items, above Delete/Archive) and `order`. Menus place them with `menuItemsAt` (`@ynput/ayon-addon/host`); Delete stays last, so a menu builds its addon `bottom` items before its destructive ones (the slicer's hierarchy hook returns `deleteContextMenuBuilder` apart for that). A `pinned` `detailsPanel.menuItem` is an icon button in the panel header (`DetailsPanelMoreMenu`, before the "more" button) instead of a menu entry.
- **Buttons (`header.item`, `projectTable.toolbarItem`).** The addon picks exactly one action: `to` (navigate), `run`, `dialog` (the host's Dialog around its content, which gets `close`), `menu` (a function returning items, shown in the shared Menu like the header's help menu) or `component` (its own JSX instead of the host's button). `checkButton` in `addon/src/slots.ts` enforces it. Both surfaces and the dev shell render them with `AddonButton` (`shared/src/components/AddonLayout/AddonButton.tsx`) and only pass their own button (`renderButton`).
- **Table columns.** `AddonColumnCell` puts the addon's cell in the table's own cell element (`TableCellContent` with the cell id): the right-click menu, selection and keyboard focus find cells by that id. Values come from the column's `fetchValues`: `ColumnValuesFetcher` asks for the rows on screen that have none (or an outdated one: the entity's `updatedAt` changed, or `refreshTableColumn`) in batches once scrolling pauses, into a store outside React (`addonColumnValues.ts`) that each cell subscribes to by entity and Copy reads (`getAddonColumnText`), since the clipboard sits above the table; paste skips addon columns.
- **Rendering.** Surfaces render a contribution with `ContributionView` (lazy piece, loading state, error boundary, slot context for `useSlot`). Menu items call `runContribution`, which reports errors as a toast. Never render a piece without one of these: an addon's crash must stay inside its own area.
- **Packages:** `addon/` is `@ynput/ayon-addon` (the API; `./manifest` is bundled into addons, `./host` is for hosts, `./check` is the manifest rules without React, for tools). `addon-dev/` is `@ynput/ayon-addon-dev` (the `ayonAddon()` Vite plugin, the `ayon-addon` CLI, the lint preset). `yarn build:addon` builds both and regenerates `addon/AGENTS.md` and `addon/dist/slots.json` from `SlotMap` (`addon/scripts/generate-docs.mjs`); a unit test fails when `addon/AGENTS.md` is stale.
- **The package imports nothing from `src/` or `@shared`, not even types**: its `.d.ts` must stand alone in an addon's `node_modules`. Public types are its own (`ProjectInfo` is the stable part of the project model). What it needs from the app (`useUser`, the store's `dispatch`, the layout components) the app registers with `provideHost` in `src/remote/addonHost.ts`, before the first render. The standalone dev shell registers its own.
- **Shared depends on the package, not the other way round.** Shared containers read the registry, so `shared/package.json` lists `@ynput/ayon-addon` as a peer and the shared build keeps it external. A copy bundled into shared would be a second registry that the standalone dev shell can't reach.

## Developing an addon in the real frontend (dev override)

`?addonDev=<addon>@http://localhost:5173` makes `RemoteModulesProvider` load that one addon from its dev server instead of the installed version (`shared/src/context/remote-modules/addonDevOverride.ts`). It is stored in localStorage until `?addonDev=off` or the banner's close button.

- **Who:** users in developer mode and service users (API-key sessions: agents, CI). Anyone else gets a console warning and the installed addons. **Where from:** `localhost`, `127.0.0.1` or `[::1]` only, so a link can't point the page at another machine's code.
- **What it loads:** `ayon-addon dev --ayon` (`@ynput/ayon-addon-dev`) serves a watched production build of the addon plus `/ayon-addon.json` (name, version, remote, modules, build id). The provider reads that file before registering the remotes, so the dev addon may differ from the installed one, or not be installed at all.
- **Reload on save:** federation can't swap a registered remote, so the banner polls `/ayon-addon.json` and reloads the page when the build id changes. Not Fast Refresh: a remote's dev-server modules need React Refresh's preamble from the page that loads them, which the host doesn't have; the watched build always works.
- Service users are treated as admins in the frontend (`src/features/user.js`), as the server does: `/api/info` doesn't send their UI exposure level, which hid project pages from API-key sessions.

## The standalone dev shell (`ayon-addon dev`)

`addon-dev/shell` renders an addon's contributions without this app: AYON's providers and the surfaces that live in shared (DetailsPanel, Slicer, SettingsPanel, the addon column cells), stand-ins for the ones that live here (header, page tabs, ProjectsList, ProjectTreeTable with its page data layer). It imports only `@ynput/ayon-frontend-shared` entries and `@ynput/ayon-addon`; what it needs from shared must be exported there (e.g. `LoginPage`, `ProjectPageLayoutHost`, `useAddonCustomizeSections`, `AddonColumnDataScope`). When a shared surface gains a provider dependency, the shell's provider stack (`addon-dev/shell/src/Shell.tsx`, `Stage.tsx`) needs it too: `ayon-addon open` on the template's contributions catches that.

## Rules and gotchas

- **Keep `hostSharedEntries.ts` and `ENTRY_NAMES` in `hostSharedModules.ts` in sync with `build.lib.entry` in `shared/vite.config.ts`.** An entry the host doesn't provide falls back to the addon's own copy, and that copy brings its own api and contexts. `tests/unit/hostSharedModules.spec.ts` checks the lists match.
- **The host never `loadShare`s these.** It imports `@shared`, `@reduxjs/toolkit`, `react-redux`, the router, react-toastify and `primereact/confirmdialog` directly. The registration only hands those same module instances to addons. Don't move them into the plugin's `shared` config: that puts every host import of them behind an async share load at startup, which slowed page loads in the benchmarks. All entries load together through one lazy module (`hostSharedEntries.ts`) the first time an addon asks for one. A separate `import()` per entry gave the build 18 extra entry points and split the host's own page chunks into many small ones (8 more requests on the dashboard). One module costs fewer, but still splits a few tiny chunks (about 5 more requests on the dashboard). Static imports instead would add about 180 KB to the main bundle. They are marked `loaded: true` so the runtime picks them over an addon's bundled copy, even a newer one. A version mismatch only logs a warning.
- **The router is shared as a list of exports, not the whole module** (`hostRouterExports.ts`). `import * as` from react-router keeps its server, framework and data router code in the main bundle (about 370 KB). The list is the declarative API, because the host runs `<BrowserRouter>`: data router APIs (loaders, fetchers, `<Form>`, `createBrowserRouter`) can't work under it. An export missing from the list is `undefined` in an addon that shares the router, so add one there when an addon needs it.
- **`registerShared` must run before any remote is registered.** It runs in `src/index.tsx` right after `init`.
- **`__esModule` on the provided module.** `@module-federation/vite` before 1.14 treats shared modules as CommonJS. Without the flag it uses the whole namespace as the default export.
- **The root reducer lives in shared** (`rootReducer`, `dynamicMiddleware`), not in `src/features/store.ts`. That lets addons inject into it at import time. The host injects its own slices with `overrideExisting: true` because the root reducer outlives a hot reloaded `store.ts`.
- **Endpoint names are global.** Every addon injects into the same api. `injectEndpoints` with `overrideExisting: false` silently skips a name that is already taken, so the addon ends up calling someone else's endpoint (this happened with `getProjectFolders`). Addons should prefix endpoint and slice names with the addon name.
- **Version skew.** An addon uses whatever the host's shared version exports. If it imports something the host doesn't have yet, that import is `undefined` at runtime. Raise the addon's minimum server version along with its `@ynput/ayon-frontend-shared` range.
- **Existing addons keep working unchanged.** An addon that doesn't declare these shares keeps its bundled copies, its own store and its own providers, the same as before.
- **Federation can't swap a remote once it is registered.** After an addon update the user is asked to refresh (`RemoteModulesProvider`).
