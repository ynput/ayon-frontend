# Representation traits

Shows the `traits` of a representation in the "Representation detail" dialog (`DetailsDialog`, Traits tab). The Raw tab keeps the old JSON view.

## Data

- `traits` comes from the representation REST entity: `{ "<trait id>": { ...trait data } }`, as written by `Representation.traits_as_dict()` in ayon-core.
- Trait definitions come from `GET /api/traits` (`useGetTraitDefinitionsQuery`, `shared/src/api/queries/traits`), mapped to `versioned id -> definition`. The backend merges the `server/traits.json` manifests of all installed addon versions, so old trait versions keep their definitions.
- No `variant` is passed on purpose: stored data may come from any installed addon version, not only the current bundle.
- A 404 means the server has no traits endpoint (older server). It is treated as "no definitions", not as an error.
- The definitions are refetched on `bundle` events, the same way as `listFrontendModules`.

## How a trait is shown

A trait can have several views. The user switches between them with the icon buttons in the trait header. `resolveTraitViews` (`utils/traitModel.ts`) lists them, default first:

1. Widget views from `registry.ts` registered under the definition's `ui.widget`.
2. File views, for traits listed in `FILE_TRAIT_LAYOUTS` (`utils/traitFields.ts`): `files:list` (a list of files) or `files:single` (one file).
3. Widget views registered under the versionless id. A view with `versions` is offered only for those trait versions, so legacy data models never reach it.
4. "Fields" (`SchemaTraitView`), when the exact trait version has a definition.
5. "Stored values" (`GenericTraitTable`), always. Traits without a definition get a "No definition" tag; its tooltip names the versions that do have one.

The picked view is remembered per versionless trait id in local storage (`representation-trait-views`). When the remembered view is not offered for a trait version, the default is used.

Definitions are data only. Never render HTML from them or load code they name.

## Trait fields across versions

Views read trait fields directly. `utils/traitFields.ts` holds the helpers that know how core trait versions differ:

- `findTraitData` finds a sibling trait by versionless id (highest version wins).
- `getFrameRange` / `getFps` read FrameRanged v1 (string `frames_per_second`) and v2 (`frame_rate_numerator` / `frame_rate_denominator`). `getHandles` reads Handles.
- `FILE_TRAIT_LAYOUTS` names where file traits keep paths, sizes and hashes (`getTraitFiles`), keyed by versioned id. `FileLocations.v1` (paths as Python strings) has none, so it shows as stored values.
- `getSchemaFieldType` repeats the server's rule for fields that can be filtered on (scalars and lists of them, no paths or regexes). "Fields" names those in the label tooltip as the typed search name (`PixelBased:display_window_width`).

### Writing a view

- A view is a component taking `TraitWidgetProps`. Add it to a list in `registry.ts` with a unique `id`, a `label` and a material `icon`. The first view of the list is the default.
- File views are keyed `files:list` / `files:single`. To give another trait the file views, add its layout to `FILE_TRAIT_LAYOUTS`.
- A view that reads several trait versions or sibling traits should go through `utils/traitFields.ts`, so version differences stay in one place. `Sequence.frame_regex` is read with `findTrait`; Python named groups are converted for JavaScript.
- Keep the data handling in pure modules (`utils/traitFields.ts`, `views/files.ts`) so unit tests can import them. Fall back to `GenericTraitTable` when the data does not have the expected shape.
- Hover details use the global tooltip: `data-tooltip` with `data-tooltip-as="pre"` for multi-line text.

Current views: `files:list` (strip, file list), `files:single` (file card), FrameRanged (timeline), PixelBased (resolution).

## Schema contract

The schemas are generated by the exporter in ayon-core (`client/ayon_core/pipeline/traits/schema.py`). It only produces this subset of JSON Schema:

- Enums are stored and listed by member name.
- `Optional[X]` is `type: [X, "null"]`, or `anyOf` for complex types.
- Nested traits are `$ref: "#/$defs/<trait id>"`.
- `format` is `path`, `regex`, or `ayon-traits`. `ayon-traits` is an object of traits keyed by id, used for Bundle items.

Property order is the field order of the trait class, and the view keeps it.

The view checks each stored value against its schema without going into nested values (`matchesSchema`). Data that older ayon-core wrote differently is shown raw with a warning icon instead of failing. For example, it stored `"GapPolicy.forbidden"` instead of `"forbidden"`, and `FileLocations.v1` lists as Python repr strings.

## Tests

- `tests/unit/representationTraits.spec.ts` tests the pure modules in `utils/`. The components import `@ynput/ayon-react-components`, so unit tests can't render them.
- `tests/unit/support/traitFixtures.ts` holds real `traits_as_dict()` output and definitions from `/api/traits`. When trait classes change, regenerate it from ayon-core rather than editing it by hand.
